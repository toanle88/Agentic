## Audit contract

A high-priority finding is one that can expose commands or credentials,
violate the read-only reviewer boundary, corrupt durable state, or make a
normal run fail on merely large input. A performance regression is actionable
when same-host p95 is more than 20% slower than its recorded baseline or peak
RSS is more than 10% higher. Measurements must identify the host and storage
conditions; safety boundaries must not be weakened to meet a timing target.

## Security result

- Issue text, repository guidance, logs, and provider output remain bounded,
  delimited evidence. They are not converted into shell code.
- Process execution continues to use argv arrays. Reviewer commands and
  OpenRouter tools retain read-only policy, path containment, and protected
  file checks.
- Sandbox runtime containers use the configured read-only root, dropped
  capabilities, resource limits, explicit network policy, and allowlisted
  environment forwarding. Reviewer mounts remain read-only.
- Sandbox image builds operate through the Docker/Podman daemon and are not a
  host security boundary. Build networking is independent from runtime
  `allow_network`, and configured credentials are not forwarded to builds.
- Redaction covers common bearer/key-value forms, provider-specific credential
  names, and configured sensitive environment values at the final durable-write
  boundary. Trusted checkouts and least-privilege environments are still
  required because heuristic redaction is not complete secret discovery.
- Complete JSON/text state is atomically replaced, so interrupted writes leave
  the previous complete artifact available. Append-only streaming logs may be
  partial; readers bound and redact them, and malformed structured output is
  never treated as approval or publication state.

## Offline performance measurement

The measurement used three cold and three warm repetitions on the same host.
The disposable corpus contained 500 valid run folders with 24 artifacts each
and one 8 MiB developer log per run; an OpenRouter tree with 1,000
directories and 10,000 files; and a Git repository with 1,000 untracked files.
Cold dashboard collection cleared the in-process snapshot cache before each
sample. Warm collection reused unchanged snapshots. No provider or network
operation was included.

Environment: Python 3.12.3; Linux 6.18.33.2-microsoft-standard-WSL2;
AMD Ryzen 5 5600GT, 12 logical CPUs; 15.3 GiB available memory at capture;
ext4 on local WSL storage. p95/p99 use the largest sample because the sample
count is three. Peak RSS is the maximum observed for the measurement process;
the dashboard render and OpenRouter measurements share that process, so their
RSS values are an upper bound rather than isolated allocations.

| Workload | p50 | p95 | p99 | observed peak RSS |
| --- | ---: | ---: | ---: | ---: |
| Dashboard collection, cold | 1.821 s | 2.377 s | 2.377 s | 41.61 MiB |
| Dashboard collection, warm | 0.130 s | 0.131 s | 0.131 s | 41.61 MiB |
| Dashboard HTML rendering | 0.064 s | 0.085 s | 0.085 s | 88.19 MiB |
| OpenRouter list, page 1 | 0.061 s | 0.062 s | 0.062 s | 88.19 MiB |
| OpenRouter list, page 34 | 0.792 s | 0.806 s | 0.806 s | 88.19 MiB |
| OpenRouter bounded read | 0.000071 s | 0.000084 s | 0.000084 s | 88.19 MiB |
| Git status, 1,000 files | 0.003 s | 0.143 s | 0.143 s | not isolated |

The cold dashboard result is 18.8% above the provisional 2 s budget, but there
is no previous same-host baseline from which to claim a regression. Warm
collection, rendering, OpenRouter inspection, and Git status were within the
initial engineering budgets. Q-12 records the cold result for follow-up; the
result does not justify weakening bounded reads, cache invalidation, path
containment, or protected-file checks.
